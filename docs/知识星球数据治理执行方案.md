# 知识星球数据治理执行方案

> 本文是交给专属 Agent 的全量执行规格。目标是一次性处理输入目录中的全部知识星球 Topic，将其转换为可追溯、可审核、可用于后续 RAG 评测的知识单元。本阶段不接入正式知识库、不修改线上检索策略，也不宣称提升最终回答效果。

## 1. 背景与目标

原始数据目录：

```text
E:\dev\project\knowledge-boll-crawler\data\raw\questions
```

当前数据不是稳定的一问一答：一个 Topic 可能包含多个子问题、编号回答、专家后续补充或纠正、普通成员讨论、占位回答、图片依赖和时效性较高的平台规则。

已知数据基线（执行 Agent 必须重新统计并报告，不能直接照抄）：

- 约 2,161 个 Topic。
- 约 4,003 条评论。
- 专家稳定身份：`owner.user_id = 844114512411242`。
- 约 721 个 Topic 含专家后续评论，共约 1,145 条。
- 大量短回答、多问多答和“稍后确认”式占位回答。

本阶段目标：

1. 无损还原每个 Topic 的讨论结构。
2. 从 Topic 中提取一个或多个问题单元。
3. 将主回答和专家后续证据正确对齐到问题单元。
4. 标记占位、补充、澄清、纠正、冲突、图片依赖和时效风险。
5. 生成一套机器产物和一套人工金标样本，供下一阶段独立测评。
6. 输入目录中的每个源文件都必须进入成功、失败或隔离清单之一；不允许只处理抽样子集后宣布完成。

本阶段不做：

- 不修改 `data/raw/questions`。
- 不上传清洗结果到正式知识库。
- 不重建正式 Chroma 集合。
- 不修改聊天问题改写、召回、重排或回答 Prompt。
- 不把普通成员评论自动当作权威答案。
- 不用 Topic ID 命中率代替答案有效性。

## 2. 领域边界

### 2.1 Topic（讨论容器）

一份知识星球 JSON 对应一个 Topic。Topic 是来源与上下文边界，不等同于一个 QA，也不直接等同于检索块。

### 2.2 问题单元（Question Unit）

Topic 内一个可独立理解、可以被单独检索和回答的用户诉求。一个 Topic 可以有 0、1 或多个问题单元。

### 2.3 证据单元（Evidence Unit）

支持某个问题单元答案的最小可引用文本或图片说明。来源可以是 `answer.text`、专家评论或图片处理结果。普通成员评论默认不是答案证据。

### 2.4 最终知识单元（Knowledge Unit）

一个问题单元及其经过对齐、排序和质量标记的证据集合。它是后续索引与评测候选，不代表已经人工认可。

## 3. 输出目录与不可变性

建议在爬虫项目旁创建独立输出，不污染源数据：

```text
E:\dev\project\knowledge-boll-crawler\data\processed\zsxq-v1\
├── manifests\
│   ├── run.json
│   ├── source-files.jsonl
│   └── statistics.json
├── normalized\
│   └── topics.jsonl
├── curated\
│   ├── knowledge-units.jsonl
│   ├── evidence-units.jsonl
│   └── rejected-units.jsonl
├── review\
│   ├── gold-sample.jsonl
│   ├── review-template.csv
│   ├── adjudicated-gold.jsonl
│   └── disagreements.jsonl
├── reports\
│   ├── data-profile.md
│   ├── extraction-quality.md
│   └── run-summary.md
└── logs\
    ├── errors.jsonl
    └── model-calls.jsonl
```

要求：

- 所有 JSONL 使用 UTF-8，每行一个完整 JSON 对象。
- 每次运行生成唯一 `run_id`、处理版本、Git commit、模型名、Prompt 版本和时间。
- 每个输出对象都必须能追溯到原文件、`topic_id` 和 JSON 字段/评论 ID。
- 重跑相同版本必须产生确定的稳定 ID；不得使用随机 UUID 作为业务 ID。
- 模型响应必须缓存，支持断点续跑，禁止失败后无限重试。

## 4. 标准数据契约

### 4.1 Normalized Topic

```json
{
  "schema_version": "zsxq-normalized-v1",
  "run_id": "...",
  "topic_id": "188111288515812",
  "source_file": ".../topic_188111288515812.json",
  "source_sha256": "...",
  "topic_type": "q&a",
  "created_at": "2024-01-17T23:44:55.330+08:00",
  "question": {
    "author_id": "...",
    "text": "...",
    "images": []
  },
  "primary_answer": {
    "author_id": "844114512411242",
    "text": "...",
    "images": []
  },
  "discussion": [
    {
      "comment_id": "...",
      "parent_comment_id": null,
      "author_id": "...",
      "author_role": "expert|member|questioner|unknown",
      "text": "...",
      "images": [],
      "created_at": "...",
      "depth": 0
    }
  ],
  "normalization_warnings": []

```

规范化阶段只还原事实结构，不总结、不改写问题、不判断答案质量。

### 4.2 Knowledge Unit

```json
{

  "knowledge_unit_id": "topic:{topic_id}:q:{question_index}",

  "question_source_spans": [

  "evidence_ids": ["topic:{topic_id}:e:1"],
  "answer_status": "complete|partial|pending|uncertain|contradicted|unanswered",
  "authority": "expert|mixed|member_only|none",
  "quality": {
    "answer_relevance": 0.0,
    "completeness": 0.0,
    "self_contained": 0.0,
    "authority": 0.0,
    "overall": 0.0
  },
  "temporal_risk": "low|medium|high",
  "requires_image": false,
  "review_state": "auto_usable|needs_review|rejected",
  "reason_codes": [],
  "extractor": {
    "method": "rule|model|hybrid",
    "model": "...",
    "prompt_version": "..."
  }
}
```

### 4.3 Evidence Unit

```json
{
  "schema_version": "zsxq-evidence-v1",
  "evidence_id": "topic:{topic_id}:e:{ordinal}",
  "topic_id": "...",
  "source_kind": "primary_answer|expert_comment|member_comment|question_image|answer_image|comment_image",
  "source_pointer": "answer.text|comments/{comment_id}/text|...",
  "author_id": "...",
  "author_role": "expert|member|questioner|unknown",
  "text": "原文证据，不允许静默改写",
  "relation": "primary_answer|supplement|clarification|correction|pending|followup_question|member_opinion|noise",
  "supports_question_indices": [1],
  "supersedes_evidence_ids": [],
  "confidence": 0.0,
  "created_at": "..."
}
```

模型生成的摘要不得冒充原始证据。若需要生成规范化答案，另建字段并保留支撑证据 ID。

## 5. 处理流水线

### 阶段 A：源数据清单和数据画像

1. 枚举所有 `.json` 文件并计算 SHA-256。
2. 严格解析 JSON；失败文件写入 `errors.jsonl`，不得静默跳过。
3. 统计字段覆盖率、长度分布、评论数量、专家评论、图片、空字段和异常类型。
4. 输出 `data-profile.md`，列出至少 20 个代表性异常样本。

验收：文件总数、成功数、失败数和输出总数可以相互核对；重复运行统计一致。

### 阶段 B：讨论结构规范化

1. 使用 `comment_id`、`parent_comment_id`、`repliee` 和时间还原评论树。
2. 专家身份只按稳定 `user_id = 844114512411242` 判定，姓名仅用于展示。
3. 图片必须保留所属位置：question、answer 或具体 comment。
4. 解析并规范化时间；无法解析时保留原值并记录 warning。
5. 缺父评论、循环父链、重复 ID 等异常必须显式记录。

验收：原始非空评论数量与 normalized 评论数量完全一致；任何丢失都有错误记录。

### 阶段 C：问题单元提取

采用“规则候选 + 模型判定”的混合方式：

1. 规则识别编号、项目符号、问号、段落边界，产生候选子问题。
2. 模型判断候选是否是独立诉求，并补全必要背景。
3. 不允许模型引入源文本没有的事实、品牌、数字或结论。
4. 对无法可靠拆分的问题保留为一个问题单元并标记 `needs_review`，禁止强拆。
5. 纯背景、寒暄、重复描述不生成独立问题单元。

每个问题必须带 `question_source_spans`；Agent 应实现自动校验，确保 `quote` 可在来源原文定位。

### 阶段 D：证据抽取与问答对齐

1. 将 `answer.text` 按语义段落拆为证据候选，不按固定字符硬切。
2. 专家评论全部进入证据分类；普通成员评论仅分类，不默认参与答案。
3. 为每条证据判断 relation，并关联支持的问题序号。
4. 识别“明天问问、稍后回复、先确认一下”等占位回答，标记 `pending`。
5. 后续专家回复若给出正式答案，应作为 `supplement` 或 `correction`；必要时标记替代的旧证据。
6. 一个证据可以支持多个问题；一个问题也可以由多条证据共同支持。
7. 无法确定对应关系时不猜，标记 `needs_review`。

模型输出必须使用结构化 JSON Schema；解析失败不得用字符串正则悄悄兜底成成功结果。

### 阶段 E：质量和风险标记

质量分不是简单按长度计算。至少判断：

- 是否回答当前问题。
- 是否覆盖问题的主要约束。
- 是否脱离 Topic 后仍能理解。
- 是否来自专家。
- 是否存在后续纠正或冲突。
- 是否依赖图片才能理解。
- 是否涉及平台规则、税务、物流、费率、准入政策等高时效内容。

建议准入规则：

- `auto_usable`：专家证据、非 pending、无未解决冲突、问题和答案可自包含、overall ≥ 0.80。
- `needs_review`：多问多答对齐不稳、图片依赖、冲突、时效风险高、overall 0.50–0.80。
- `rejected`：没有有效答案、只有普通成员观点、纯联系方式/口令/噪声、overall < 0.50。

阈值必须集中配置并写入 run manifest，不得散落硬编码。

### 阶段 F：全量处理后的人工质量审计

自动治理必须覆盖全部 Topic。完成全量处理后，再从全量产物中分层抽取至少 300 个 Topic 进行人工质量审计，抽样仅用于验证质量，不能替代或限制全量处理：

- 50 个单问单答。
- 60 个明显多问多答。
- 60 个含专家后续评论。
- 40 个主回答疑似 pending/低质量。
- 40 个含图片。
- 50 个冲突、高时效或无法自动判定样本。

同一个 Topic 可属于多个层，但最终必须保证至少 300 个唯一 Topic。随机种子固定并记录。所有 `needs_review` 和 `rejected` 结果都必须保留在全量产物中，不能因为不在人工审计样本里而丢弃。

每个样本由人工标注：

- 正确问题单元数量和文本。
- 每个问题对应的证据 ID。
- 证据 relation。
- answer_status。
- 可否用于直接回答。
- 模型是否添加源外事实。

优先双人独立标注至少 50 个样本，并记录分歧与裁决；如只有一名标注者，必须在报告中明确局限。

## 6. 质量指标与门槛

自动产物必须对照人工金标计算：

| 指标 | 定义 | 最低门槛 |
|---|---|---:|
| Question Boundary F1 | 提取问题单元边界是否正确 | ≥ 0.90 |
| Evidence Alignment Precision | 自动关联证据中真正支持该问题的比例 | ≥ 0.92 |
| Evidence Alignment Recall | 金标支持证据被正确关联的比例 | ≥ 0.88 |
| Pending Precision | 标记为 pending 的证据确为占位回答 | ≥ 0.95 |
| Expert Attribution Accuracy | 专家身份与证据归属正确率 | = 1.00 |
| Unsupported Fact Rate | 规范化问题/答案出现源外事实比例 | ≤ 1% |
| Traceability | 输出对象可定位原文的比例 | = 100% |
| Auto-usable Precision | 自动准入单元确实可用于回答的比例 | ≥ 0.95 |

门槛未达到时不得宣布全量清洗完成；应输出失败类别、代表样本和下一轮修正建议。

## 7. 测试要求

至少包含：

1. 单问单答。
2. 编号多问多答且严格一一对应。
3. 多问但回答合并陈述。
4. 主回答 pending、专家评论给出最终答案。
5. 专家评论纠正主回答。
6. 普通成员评论很多但无专家确认。
7. 评论父链、回复链和缺失父节点。
8. 空回答、极短回答、纯链接、联系方式、表情。
9. 问题/回答/评论图片归属。
10. 重跑稳定 ID 和模型缓存。
11. 模型结构化响应非法、超时、限流和断点续跑。
12. 原文件零修改校验。

测试使用脱敏的小型 fixture，不将真实全量数据复制进代码仓库。

## 8. Agent 实施顺序

专属 Agent 应按以下顺序执行并逐阶段提交可运行结果：

1. 检查目标仓库现状、AGENTS/README 和已有脚本，确定代码放置位置。
2. 实现 manifest、稳定 ID、JSONL I/O、缓存和错误记录。
3. 实现源画像与 normalized Topic。
4. 完成规则候选提取及单元测试。
5. 定义版本化模型 Prompt 和 JSON Schema。
6. 实现问题提取、证据分类与对齐。
7. 实现质量评分、风险标记和准入分层。
8. 全量 dry-run，先输出统计，不生成 curated 准入结果。
9. 人工检查至少 50 个异常样本，修正规则/Prompt。
10. 对输入目录全部 Topic 正式运行；不得设置抽样上限。
11. 从全量结果生成至少 300 个唯一 Topic 的分层质量审计包并完成可获得的人工标注。
12. 计算质量指标并形成最终报告。

开发调试期间可以使用固定小型 fixture 验证代码，但正式交付必须处理全部 2,000 多个 Topic。Prompt 冻结后执行一次全量正式运行；若全量运行中修改了规则或 Prompt，必须提升处理版本并重新处理受影响的全部 Topic，不能留下混合版本产物。

## 9. 最终交付物

Agent 完成后必须交付：

- 可重复运行的一条命令及参数说明。
- 源画像、normalized、curated、rejected、review 全部产物。
- 版本化 JSON Schema 与 Prompt。
- 自动测试及测试结果。
- 全量运行 manifest、错误日志和模型调用统计。
- 至少 300 个唯一 Topic 的人工质量审计金标与分歧记录。
- 指标报告，包含总体结果和各复杂度分层结果。
- 至少 20 个失败案例分析。
- 明确列出仍不能自动处理的情况。
- Git diff/commit 范围说明，不得混入无关修改。

## 10. 交接给下一阶段测评的信息

清洗 Agent 结束后，请向测评方提供：

1. 输出根目录和 `run_id`。
2. 源文件数、normalized Topic 数、Knowledge Unit 数、Evidence Unit 数。
3. `auto_usable / needs_review / rejected` 数量。
4. 使用的模型、Prompt 版本和配置阈值。
5. 人工金标文件及标注说明。
6. 所有质量指标及逐样本预测结果。
7. 失败/跳过文件和未解决问题。

下一阶段会先核对源文件总数与全量处理覆盖率，再独立验证数据泄漏、质量审计样本代表性、问题拆分、证据对齐、拒答样本，并在全部清洗产物上重新构建索引和测试，在金标子集上计算 Evidence Recall、Evidence Precision 和最终回答有效性。
