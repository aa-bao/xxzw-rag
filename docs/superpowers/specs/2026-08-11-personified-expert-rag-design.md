# 拟人化专家 RAG 总体设计

日期：2026-08-11

状态：已确认，等待实施

关联决策：[ADR-0028](../../adr/0028-expert-assistant-is-rag-not-agent.md)

## 1. 结论

系统新增通用的“专家助手”能力，仲帅作为第一个实例。目标是在保留原始证据和引用的前提下，让回答同时体现专家公开材料中的判断顺序与表达习惯。

这不是 Agent，也不实现 Skill 运行系统。在线链路保持为固定的 RAG：问题改写、检索、重排、上下文组装、提示词生成和流式回答。人物材料的清理、公开表达画像和可选专家规则均在离线流程完成。

```text
原始证据 ---------------------------> 事实与引用
公开表达画像 -----------------------> 回答组织与措辞
经审核的专家规则（验证有效后启用） -> 诊断顺序与判断方法
```

正式产品名称使用“仲帅AI助手”或“基于仲帅材料的AI助手”，不得让用户误认为真人在线。

## 2. 当前事实基线

### 2.1 数据

截至本设计确认时，`knowledge-boll-crawler` 中包含：

- 136 篇精选长帖；
- 2159 条有文本的正式问答；
- 精选帖和问答评论中大量仲帅本人补充回复；
- 约 3641 条可用于公开表达画像的第一人称正式回答或回复。

数据仍可能继续增长，所有产物必须记录源数据快照、数量和内容哈希，不能把以上数量写成业务常量。

### 2.2 当前 RAG 查询链路

当前 `QueryEngine` 的线上链路实际使用 `ChromaRetrieval`。它先取得向量候选，再只在向量候选内部计算简单字符词法分数；独立 `FtsIndex` 已有实现与测试，但尚未接入聊天生产链路。云端 reranker 的实现、配置、迁移和运行时接线也尚不存在。

因此，真正的 Chroma + FTS5 独立双路召回、RRF 与云端 reranker 是本功能的前置依赖，必须先完成并通过回归评测。

## 3. 目标

- 将帖子、完整问答和带问题上下文的专家回复转换为可追溯的原始证据记录。
- 精确召回 `9610`、`9810`、SKU、ROI、FBA 等术语，同时支持自然语言改写后的语义召回。
- 为一次对话选择一个版本化专家配置，使同一知识库既可普通问答，也可使用专家公开答疑风格。
- 事实陈述始终引用原始证据；画像和派生规则不能成为事实来源。
- 通过 A/B/C 评测分别验证基础 RAG、公开表达画像和专家规则的增益。
- 所有专家结构均通用，不在 RAG 核心写入知识星球或仲帅专用字段。

## 4. 非目标

- 不实现工具调用、任务规划、执行循环或自主操作店铺。
- 不加载 Codex/Claude Code `SKILL.md`。
- 不做模型权重训练或传统知识蒸馏。
- 不推断私人人格、情绪、家庭、人际关系或压力行为。
- 不下载或绕过权限获取视频；视频继续作为独立 TODO。
- 不自动公开分发付费材料；部署和材料使用必须符合授权范围。
- 首版不自动发布 LLM 提炼的画像或规则，必须人工审核。

## 5. 领域模型

### 5.1 ExpertProfile

专家助手的稳定身份，归属于一个用户空间。它不拥有知识库，用户在创建对话时独立选择专家配置和一个或多个知识库。

### 5.2 ExpertProfileVersion

不可变的专家配置快照，包含身份声明、适用领域、公开表达画像、硬约束、来源快照与审核状态。对话绑定具体版本，后续画像更新不会悄悄改变已有对话行为。

### 5.3 EvidenceRecord

专家本人内容形成的可引用记录。问题文本和其他成员评论可以作为上下文，但只有明确标记为专家本人的内容构成专家事实证据。

### 5.4 ExpertRule

从多个独立证据家族中归纳的诊断流程、条件判断、执行顺序、检查清单、风险边界、例外或追问规则。规则不是原话，只有经过支持、审核、时效与发布四重门槛后才能参与线上分析。

### 5.5 RuleEvidence

专家规则与原始证据间的多对多关系，关系类型为 `supports`、`qualifies` 或 `contradicts`。结构父子关系继续使用 `parent_id`，不得复用它表达规则溯源。

## 6. 仓库职责

### 6.1 knowledge-boll-crawler

负责所有离线、来源相关工作：

- 保存不可变 raw 数据；
- 作者身份解析和上下文重建；
- 输出 `evidence_records.jsonl`；
- 划分训练、开发和留出主题；
- 生成并人工审核 `voice_profile.json`；
- 在 B/C 评测证明有价值后生成 `expert_rules.jsonl` 与 `rule_provenance.jsonl`；
- 保存源快照、转换报告和评测集。

### 6.2 rag-database

负责通用在线能力：

- 通用 JSON/JSONL 入库；
- Chroma + FTS5 + RRF + 可选 reranker；
- ExpertProfile 与不可变版本管理；
- 对话绑定专家版本；
- 专家 Prompt 组装；
- 原始证据引用；
- 在规则层启用后执行分路召回和证据展开；
- 安全、所有权、审计和回归评测。

### 6.3 colleague-skill

仅作为离线研究和提炼参考。可以固定上游提交，复用或改造其 Work Analyzer、Persona Analyzer 中与公开表达有关的部分、Builder、增量合并和纠正思想。不得作为线上运行依赖，也不得直接把生成的 `work.md` 当作正式知识。

若复制其代码、提示词或模板，必须保留 MIT 许可证和版权声明。

## 7. 原始证据契约

### 7.1 标准记录

```json
{
  "record_id": "qa:1521211588212422",
  "parent_id": null,
  "record_type": "expert_qa",
  "title": "店铺转化率低应该怎样排查",
  "content": "问题：……\n\n仲帅回答：……",
  "keywords": ["转化率", "价格", "评价", "市场需求"],
  "filters": {
    "layer": "evidence",
    "expert_id": "zhongshuai",
    "author_role": "expert",
    "source_type": "question_answer",
    "source_section": "questions",
    "has_media": false,
    "text_complete": true
  },
  "timestamps": {"source_time": "..."},
  "display": {
    "question_author": "...",
    "expert_name": "仲帅 速卖通认证讲师"
  },
  "source_pointer": "data/raw/questions/topic_1521211588212422.json#",
  "raw": {}
}
```

### 7.2 上下文规则

- 正式问题与专家回答生成一个 `atomic` 记录，不得分离。
- 帖内多个“问/答”拆成多个原子问答；拆分后不再把同一全文重复索引。
- 专家评论回复必须带帖子主题、被回复内容和最短必要前序上下文。
- 普通成员评论只作为上下文，默认不独立建立专家知识索引。
- 图片或视频回复保留 raw 与缺失标记，但没有文本时不进入文本索引。
- 文本清理只解码平台标签、URL、空白和展示格式，不润色或改写专家原文。

### 7.3 稳定身份

- 问答使用平台 `topic_id` 和 `comment_id`。
- 精选帖应优先补抓平台 ID；补抓前使用源文件内容哈希形成 legacy ID，不把 `topic_index` 当永久身份。
- 无评论 ID 的旧记录使用父记录 ID、作者、时间和文本哈希生成确定性 ID。

### 7.4 索引投影

- `embedding_text`：主题、完整问题和专家回答。
- `lexical_title`：人工或确定性生成的可读主题。
- `lexical_content`：问题原文和回答原文。
- `lexical_keywords`：只使用原文真实出现或人工确认的术语。
- 所有专业编号、金额、比例和日期必须保持原样。

## 8. 公开表达画像

`voice_profile.json` 是简短、版本化、人工审核的系统配置，不写入向量或全文索引。它只描述公开教学和答疑方式，包括：

- 结论优先；
- 先纠正错误前提；
- 先定位根因再给执行动作；
- 简单问题短答，复杂问题编号拆解；
- 信息不足时追问关键条件；
- 高风险问题明确劝阻；
- 未核实和强时效内容保留不确定性。

不得机械要求每条回答使用省略号、口头禅、错别字、训斥或夸张语气。画像建议控制在 500–1000 个中文字符，避免压过证据和用户问题。

每个画像版本至少记录：来源快照、样本数、生成模型、提炼提示词版本、人工审核状态和纠正记录。

## 9. 专家规则

规则层为条件启用项。只有 B/C 评测证明它明显优于“证据 + 画像”时，才实现完整线上规则召回。

正式规则状态拆为：

```text
evidence_status: candidate | supported | disputed | deprecated
review_status: pending | approved | needs_changes | rejected
freshness_status: fresh | review_due | stale | superseded
publication_status: draft | published | superseded
```

只有 `supported + approved + fresh + published` 的规则参与线上分析。政策、税务、关税和平台机制必须记录观察日期与复核日期；过期规则不得提供确定性建议。

## 10. 在线查询流程

### 10.1 无规则的 MVP

```text
用户问题
  -> 结合对话历史改写检索问题
  -> HybridRetrievalModule
       Chroma dense Top N
       FTS5 BM25 Top N
       RRF
       可选云端 reranker
  -> 父记录/相邻块上下文扩展
  -> PromptComposer(base safety + ExpertProfileVersion + evidence)
  -> LLM 流式回答
  -> 原始证据引用
```

### 10.2 规则验证通过后的扩展

```text
证据 lane：layer=evidence Top 6
规则 lane：layer=derived 且发布状态有效 Top 3
  -> 为命中规则解析 RuleEvidence
  -> 确保支持该规则的原始证据进入上下文
  -> 规则用于组织分析，引用仍指向原始证据
```

这仍是固定查询流程，不包含模型自主选择工具或循环执行。

## 11. Prompt 约束

系统层顺序：

1. 现有不可信检索内容、引用与拒答约束；
2. AI 身份声明和专家适用范围；
3. 公开表达画像；
4. 禁止冒充、禁止补全私人人格、禁止把推断说成原话。

规则和原始证据都放入结构化的不可信上下文区，不能覆盖系统指令。事实必须引用原始证据；当材料不足、相互冲突或明显过期时必须说明。

## 12. 数据集与评测

在任何画像或规则提炼之前，以完整主题为单位划分训练、开发和留出集。同一主题的正文、问题、回答和全部评论必须位于同一集合，避免上下文泄漏。

人工黄金集至少 100 题：

- 25 条原文事实题；
- 25 条条件判断题；
- 20 条新场景迁移题；
- 10 条材料不足题；
- 10 条冲突与时效题；
- 10 条多轮追问题。

依次比较：

```text
A：原始证据 + 普通 Prompt
B：原始证据 + voice_profile
C：原始证据 + voice_profile + expert_rules
```

上线硬门槛：

- 事实与引用准确率不低于 95%；
- 关键条件保留率不低于 90%；
- 强时效规则日期保留率为 100%；
- 严重虚构、错误作者归属和身份冒充均为 0；
- 无依据问题正确拒答率不低于 90%。

B 的风格得分必须显著优于 A，且事实准确率下降不得超过 2 个百分点。只有 C 的新场景判断路径显著优于 B，才保留规则层。

## 13. 安全、权限与材料边界

- ExpertProfile、版本、对话、文档、规则和评测资产都受用户空间所有权限制。
- 专家配置必须显示“AI助手，不是本人”的身份声明。
- 不把付费材料大段复现给无权限用户，不支持公开导出整套原始语料。
- 检索片段继续视为不可信数据，不能触发操作。
- 画像与规则提炼过程不得发送未授权材料到未经批准的模型服务。
- 日志不记录完整付费内容、模型密钥或不必要的个人信息。

## 14. 发布阶段

1. 完成真实混合检索和 reranker 接线。
2. 导出原始证据并建立普通 RAG 基线。
3. 新增版本化 ExpertProfile，运行 A/B。
4. 若 B 通过，发布“仲帅AI助手”MVP。
5. 小规模提炼 30–50 条规则并运行 B/C。
6. 只有 C 通过，才实现规则证据展开和全量规则生命周期。

旧的 `zhongshuai-work/work.md` 是已废弃概念试点，不属于正式架构或运行输入。
