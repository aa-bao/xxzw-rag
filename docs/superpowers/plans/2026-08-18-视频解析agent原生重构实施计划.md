## 一、背景与目标

### 1.1 背景

当前「AI 视频分析」模块通过 subprocess 直接调用外部仓库
`E:\dev\project\quick-watch\scripts\quick_watch.py`（约 2200 行）完成视频解析，
`rag-service/src/video/` 只是薄壳（config/service/router）。问题：

1. **外部脚本依赖**：核心流水线（下载、字幕、ASR 分片转写、关键帧、报告）全部在
   quick-watch 仓库中，与本系统解耦；quick-watch 版本变化、仓库移动都会破坏功能。
2. **模型配置缺失**：ASR 模型名硬编码 `qwen3-asr-flash-filetrans`（quick_watch.py 第 32 行 MODEL），DashScope Key 只从环境变量读取；Chat 模型在设置页是 disabled 占位，无法在 agent设置页配置。
3. **报告链路未打通**：HTML 报告依赖 quick-watch 的 render_report.py + 模板，summary.json 生成流程未接入本系统，前端「HTML 报告」按钮实际不可用（交接文档遗留待办）。
4. **设置页内容单薄**：agent设置只有「运行环境」只读信息 + 帧数偏好，「语音模型、chat 模型都要能设置」的用户诉求未满足。

### 1.2 目标

把视频解析能力**内建到本系统**，成为一个真正的视频解析 agent：

1. **流水线原生化**：将 quick-watch 的获取→字幕→音频→ASR→合并→关键帧→报告全流程移植为 `rag-service/src/video/` 内的 Python 模块，不再 subprocess 调用外部脚本。
2. **模型可配置**：agent设置页可配置 **语音模型（ASR）** 与 **Chat 模型**（问答/摘要），配置持久化到数据库并支持运行时热更新与连接测试。
3. **报告闭环**：摘要生成（Chat 模型）+ HTML 报告渲染内建，前端报告按钮可用。
4. **保持既有 UI 体验**：视频分析页、视频数据库页交互不变，设置页扩展为完整配置页。

### 1.3 不做的事

- 不重做前端视频分析/视频数据库页面的交互逻辑（仅按需小改）。
- 不删除 quick-watch 仓库本身（可继续独立使用），本系统不再依赖它运行。
- 不引入新的外部服务；继续使用 yt-dlp / ffmpeg / DashScope（这些是运行时工具依赖，通过 pyproject 声明，不属于外部脚本）。

### 3.2 视频 Agent 设置模型（核心新增）

新增单行配置表 `video_setting`（参照 rag_model_setting 模式），字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK | 恒为 1（单行） |
| asr_provider | VARCHAR(50) | 固定 dashscope（首版） |
| asr_model | VARCHAR(200) | 语音模型名，默认 qwen3-asr-flash-filetrans |
| asr_api_key | VARCHAR(1000) | DashScope Key（不回显，只暴露 has_asr_api_key） |
| chat_base_url | VARCHAR(500) | Chat 模型 base_url（空 = 复用系统 model_relay） |
| chat_model | VARCHAR(200) | Chat 模型名（空 = 复用系统 chat_model） |
| chat_api_key | VARCHAR(1000) | Chat Key（空 = 复用系统 key） |
| frames | INT | 默认关键帧数，默认 12 |
| updated_at | DATETIME | 更新时间 |

语义：
- **ASR 必配**（独立于系统模型）：asr_model + asr_api_key。
- **Chat 可覆盖**：chat_base_url/chat_model/chat_api_key 为空时回退到系统 RuntimeModelRelay 的 model_relay 配置（问答/摘要用同一 ChatClient 通道）；非空时用视频 agent 独立配置。
- 运行时内存态：新增 `VideoAgentSettings` dataclass（仿 RuntimeModelRelay），保存时同步 DB，热更新立即生效，响应不回显密钥。

### 3.3 流水线设计（service.py 重写）

任务状态机沿用现有文件持久化（<task_root>/<task_id>.json），执行改为**纯 asyncio 原生编排**（不再 subprocess quick_watch.py）：

```text
submit(source, kind, frames)
  └─ run():
       stage=downloading
       ├─ URL: validate → 微信解析(可选) → try_url_captions
       │        ├─ 字幕覆盖达标 → transcript=captions
       │        └─ 否则 → acquire_url_audio（yt-dlp → 浏览器兜底）
       ├─ 本地文件: ffmpeg 提取音频
       stage=transcribing
       ├─ detect_silence_points → plan_asr_chunks
       ├─ 并发 transcribe_chunk（asyncio.gather + 信号量，默认 3 worker）
       │     └─ DashScope OSS 上传 + QwenTranscription 同步轮询
       ├─ merge_chunk_results / merge_caption_and_asr
       stage=extracting_frames（与 ASR 并行，asyncio.create_task）
       ├─ 下载低码率视频（URL 场景）→ extract_keyframes → 复制到 output_dir/frames
       stage=summarizing
       ├─ summary.py：ChatClient.complete 生成摘要/要点/视觉说明（summary.json）
       stage=rendering_report
       └─ report.py：渲染 report.html 到 output_dir
```

并行策略：ASR 转写与关键帧提取并发（asyncio.create_task 双协程），与现状 quick-watch 的 ThreadPoolExecutor 双线程等价。

### 3.4 报告生成（summary.py + report.py）

- **summary.py**：prompt 组装（系统提示 + 转录文本前 12000 字符 + 关键帧视觉说明可选），调用 ChatClient 生成 {summary, keypoints, visual_notes, title}，写 `output_dir/summary.json`。
- **report.py**：移植 render_report.py 的模板逻辑（general 通用模板 + BASE_CSS），生成自包含 `report.html`（base64 内嵌关键帧、转录时间线、成本明细）。首版只移植通用模板，专家模板（film_storyboard 等）后续迭代。

## 九、风险与注意

- **DashScope ASR 依赖**：OSS 上传 + 轮询同步 API，网络异常要按分片重试；建议保留 quick-watch 的 retries 语义（每分片 1-2 次重试）。

- **配置优先级**：chat_* 空 = 复用系统 model_relay；实现时注意 `model_fields_set` 语义区分「未传」与「空串」（参照 router_settings.py 的写法）。
- **报告模板**：首版只做通用模板，专家模板后续迭代；报告失败不影响转录结果展示。
- **不用删除** quick-watch 仓库；本系统只是不再依赖。
