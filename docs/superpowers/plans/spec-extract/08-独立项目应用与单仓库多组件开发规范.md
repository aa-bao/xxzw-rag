## 1. 目的

- 本规范定义新项目如何在不修改主系统 Vue、Java 和固定菜单的前提下，完成一次开发后即可由主系统登记、由 Project Platform Controller 部署，并通过主系统通用项目容器嵌入运营页面。
- 本规范是**项目开发者的交付契约**。
- 平台能力尚未上线的环境可以提前完成项目开发和契约门禁，但**不得绕过主系统手工模拟为已接入生产**。

## 2. 适用模式

- 新项目**默认**使用：

```text
integrationMode: EMBEDDED_APP
```

- `EMBEDDED_APP` 适用于包含以下**任一**能力的项目：
  - 面向运营人员的独立工作台。
  - 项目自己的后端 API 和业务数据。
  - 项目自己的数据库 Schema。
  - 一个仓库内存在多个 Windows 执行器。
  - 需要独立发布、回滚、停用和健康检查。
- 仅有一个 Windows 执行器且不需要以上能力时，可继续使用 `LEGACY_AGENT_PROJECT`。

## 3. 职责边界

- 四类角色的职责边界（不得越界）：

```text
主系统
  用户、部门、角色、权限、项目登记、统一业务队列、Task、Attempt、Claim、节点和审计

Project Platform Controller
  服务端组件、数据库迁移、运行密钥、路由、健康、期望状态、发布和回滚

Windows Agent
  执行器制品校验、任务领取、本机进程监管、事件、日志、报告和产物

项目应用
  运营页面、业务 API、项目业务数据、业务幂等、项目内部步骤和结果
```

- **项目不得复制主系统用户表、角色表、部门表、全局业务队列、Task 状态机或节点调度器。**

## 4. 仓库结构

- 一个业务项目**必须**只有一个生产源码仓库。
- 推荐结构（逐字保留）：

```text
<project>/
|-- apps/
|   |-- frontend/
|   `-- backend/
|-- executors/
|   |-- <executor-a>/
|   |   |-- rpa-project.yml
|   |   `-- ...
|   `-- <executor-b>/
|       |-- rpa-project.yml
|       `-- ...
|-- contracts/
|   |-- openapi/
|   |-- task-types/
|   |-- reports/
|   `-- events/
|-- migrations/
|-- scripts/
|-- rpa-application.yaml
|-- RESOURCE.md
`-- README.md
```

约束：

- 组件用途**只能**由 `rpa-application.yaml` 声明，**不能根据目录名猜测**。
- 一个执行器**只能**属于一个 `appKey`。
- 共享代码可以放在仓库内公共包，但发布时**每个组件必须形成独立不可变制品**。
- 项目**不得依赖仓库外相对路径、本机目录或未登记的其他仓库**。

## 5. 应用级根清单

- 仓库根目录**必须**提供 `rpa-application.yaml`。
- 完整示例（逐字保留，含全部字段名、枚举值、路径、资源数值）：

```yaml
apiVersion: tyt-rpa/v1
appKey: auto-parts-listing
displayName: 汽配上品
description: 汽配商品草稿生成与运营审核工作台
integrationMode: EMBEDDED_APP

components:
  frontend:
    type: WEB_FRONTEND
    path: apps/frontend
    deployTarget: SERVER
    image: registry.local/auto-parts-listing/frontend
    basePathMode: RELATIVE
    resources:
      cpus: 0.5
      memoryMb: 256
      pidsLimit: 128
      tmpfsMb: 32

  backend:
    type: WEB_BACKEND
    path: apps/backend
    deployTarget: SERVER
    image: registry.local/auto-parts-listing/backend
    port: 8080
    healthPath: /platform/health
    readinessPath: /platform/readiness
    versionPath: /platform/version
    resources:
      cpus: 1
      memoryMb: 512
      pidsLimit: 256
      tmpfsMb: 64

  executors:
    - key: auto-parts-draft
      type: WINDOWS_EXECUTOR
      path: executors/auto-parts-draft
      manifest: executors/auto-parts-draft/rpa-project.yml
      distributionMode: ARTIFACT
      taskTypes:
        - AUTO_PARTS.LISTING
      requiredCapabilities:
        - PYTHON_312
        - BITBROWSER

permissions:
  - code: auto-parts-listing:project:view
    name: 进入汽配上品项目
  - code: auto-parts-listing:queue:create
    name: 创建汽配上品排队
  - code: auto-parts-listing:operation-log:view
    name: 查看运营日志
  - code: auto-parts-listing:technical-log:view
    name: 查看技术日志

database:
  primarySchema: auto_parts_listing
  migration:
    type: FLYWAY
    path: migrations
    checksumFile: migrations.sha256
```

## 6. 根清单规则

- `apiVersion` **必须**是平台已支持版本。
- `appKey` 发布后**不可变**，使用小写字母、数字和连字符；**不能占用平台保留命名空间**。
- `displayName` 用于主系统项目列表，**不作为数据库键或权限判断条件**。
- `integrationMode` 只有两个合法取值，且与组件声明强绑定：
  - `EMBEDDED_APP`：**必须同时声明 `frontend` 和 `backend`**，缺任一即判清单非法。
  - `PLATFORM_EXECUTOR`：允许只声明 `executors`；此类应用只对管理员显示，不会生成面向运营的入口。
  - 只有执行器、尚无前后端的项目**应**先用 `PLATFORM_EXECUTOR` 接入，待前后端就位后再切换为 `EMBEDDED_APP`。
- `components` 只允许 `frontend`、`backend`、`executors` 三个键，**多余键即判非法**。
- 权限字符**必须**以 `<appKey>:` 开头，且**必须包含 `<appKey>:project:view`**。
- 每个执行器清单里的 `projectKey` **必须**等于根清单的 `appKey`。
- 执行器 `key` **不得重复**；所有执行器的 `taskTypes` 合并后**不得重复**。
- 根清单**不得**包含密码、Token、数据库连接串、生产域名或服务器地址。
- 组件路径**必须**位于仓库内，**禁止绝对路径、目录穿越、符号链接和 Junction 逃逸**。
- `WEB_FRONTEND` 和 `WEB_BACKEND` **必须**声明 CPU、内存、PID 和临时盘限制。
- 服务端组件统一交付 Docker 镜像；Windows 执行器统一交付不可变制品。
- 未使用的组件字段应省略，**不能填写虚假占位组件**。
- 未被平台 Schema 声明的字段**必须拒绝，不能静默忽略**。

### 6.1 侧边栏导航声明

- 项目把侧边栏结构声明在根清单里，发布时由主系统投影成侧边栏菜单；**嵌入运行时项目不再显示自己的侧边栏**（交叉引用：规范 10 §4），只渲染内容区。
- 示例（逐字保留，含全部字段、注释语义）：

```yaml
navigation:                          # 可选。不声明即保持"目录 + 单个工作台"的旧形态
  - key: store-operations            # 小写字母数字连字符，1-64 字符，同级唯一
    name: 店铺营业数据                 # 菜单显示名
    icon: data-line                  # 可选
    status: AVAILABLE                # 可选，默认 AVAILABLE
    permission: boss-shop-data:shop-data:view   # 可选，控制该菜单对谁可见
    children:                        # 目录节点：有 children
      - key: operations-overview
        name: 经营总览
        children:
          - key: shop-data
            name: 店铺数据
            route: /shop-data?view=shop-total   # 页面节点：有 route
          - key: shop-dashboard
            name: 店铺数据看板
            status: PLANNED          # 声明了，但不会出现在侧边栏
            route: /dashboard
```

规则：

- **目录与页面二选一**：有 `children` 就不能有 `route`，反之亦然；两者都没有即判非法。
- **`route` 必须是同源相对路径**：单个前导 `/`，**禁止 `//host`、绝对 URL、`..` 穿越和反斜杠**。该值由容器透传给项目前端做深链，放宽会让一个菜单项把 iframe 导去其它站点。
- **`status: PLANNED` 声明但不投影**：这是契约的一部分，不是平台的隐式行为。节点写在清单里表达"计划建设"，平台不会为它生成菜单；项目实现后改成 `AVAILABLE` 并重新发布，菜单即出现。
  - 背景约束（契约事实）：`sys_menu` 没有禁用态，`status=1` 的行会被侧边栏查询整行过滤；要做置灰得给主系统核心表加列并改共享侧边栏组件，代价与收益不成比例。
- `permission` 省略时该菜单跟随应用的 `<appKey>:project:view`。
- **`navigation` 是可选的**：未声明的应用行为完全不变，仍是"应用目录 + 一个工作台页面"。
- 一级节点通常对应业务领域下的一个项目（如 BOSS 业务领域系统下的"店铺营业数据"），今后新增项目即在此追加一个一级节点。

### 6.2 字段取值边界

- 平台对清单是**严格校验**：不合规直接判非法，错误信息**不会指出是哪个字段越界**。
- 字段边界表（逐字保留，含全部正则、数值范围）：

| 字段 | 约束 |
|---|---|
| `appKey` | `[a-z0-9][a-z0-9-]{1,62}[a-z0-9]`，3–64 字符，**不能以连字符开头或结尾** |
| `displayName` / `description` / `icon` | 200 / 1000 / 100 字符上限 |
| `image` | 500 字符上限 |
| `resources.cpus` | 0.1 – 8 |
| `resources.memoryMb` | 64 – 8192 |
| `resources.pidsLimit` | 32 – 2048 |
| `resources.tmpfsMb` | 16 – 512 |
| `backend.port` | 1 – 65535 |
| 执行器 `key` | `[a-z0-9][a-z0-9._-]{1,99}`，小写 |
| `taskTypes[]` | `[A-Z][A-Z0-9_.-]{1,127}`，**必须全大写** |
| `requiredCapabilities[]` | `[A-Z][A-Z0-9_]{1,63}`，**必须全大写，不含连字符和点** |
| `permissions[].code` / `.name` | 160 / 200 字符上限，`code` 必须以 `<appKey>:` 开头且不重复 |
| `database.primarySchema` | `[a-z][a-z0-9_]{1,62}`，小写下划线，不能用连字符 |
| `navigation` 深度 | 最多 5 层 |
| `navigation` 节点总数 | 最多 200（整棵树合计，不是每层） |
| `navigation[].key` | `[a-z0-9]` 开头结尾，最长 64，**同级唯一** |

例子里没出现、但合法的字段：

- 根级 `icon`：应用在侧边栏的图标。
- `components.executors[].entrypoint`：执行器入口，仓库内相对路径。
- `components.executors[].distributionMode`：省略时默认 `GIT`，另一合法值是 `ARTIFACT`。
- `database.migration.changelogFile`：`type: LIQUIBASE` 时**必填**，`FLYWAY` 时省略。

## 7. 前端组件

前端必须：

- 支持 `embedded=true`，嵌入时隐藏自身全局导航和重复登录入口。
- 声明了 `navigation`（§6.1）的项目，嵌入时必须**隐藏自身侧边栏**，只渲染内容区；并且必须能按容器透传的 `route` 直接打开对应页面，而不是永远落在默认首页。项目内部的标签页、筛选器和详情页仍可保留（交叉引用：规范 10 §4）。
- `route` 作为表单字段随 SSO bootstrap 一起提交（字段名 `route`，未声明 navigation 时不传）。项目后端在用它拼重定向地址前**必须自行校验为同源相对路径**——单个前导 `/`，拒绝 `//host`、绝对 URL 与 `..`。原因（契约事实）：清单解析时虽已校验过，但到达后端的是浏览器提交的表单值，不等于清单里声明的值；不校验就直接拼进 `Location`，等于把开放重定向送给任何能构造该表单的人。
- 使用相对静态资源路径，`basePathMode` 固定为 `RELATIVE`。
- **调用自己后端的所有请求也必须用相对路径，并带上 `credentials: 'same-origin'`**。应用挂在 `/project-apps/<appKey>/` 前缀下，`fetch("/platform/session")` 这种根路径写法会打到**主系统根域**而不是项目自己。正误对照（逐字保留）：

```js
// 错误：打到 https://<主系统>/platform/session
fetch("/platform/session")
// 正确
fetch("./platform/session", { credentials: "same-origin" })
```

  - 该错误的迷惑性（排查线索，契约事实）：SSO 握手其实成功了（后端日志可见 `authorization exchange completed / httpStatus 200`），但前端拿会话时打到了主系统，拿回一个结构对不上的响应，于是渲染成"未授权，请从主系统项目入口进入"。容易误判成 SSO 或权限问题，实际是一行路径写法。
- **不写死**主系统域名、项目生产域名或 API 主机。
- 通过项目后端会话获取用户、部门、权限和数据范围。
- 所有按钮权限**同时在后端校验**，不能只做前端隐藏。
- 处理会话过期并回到主系统通用项目容器，**不保存主系统 JWT**。
- 在桌面和目标运营分辨率下完成无重叠、无横向内容丢失的视觉验收。

## 8. 后端组件

后端必须：

- 提供健康、就绪和版本接口。
- 使用 Controller 注入的项目专属运行账号，**只访问当前项目 Schema**。
- 执行租户、部门、数据范围和权限校验。
- 保存项目业务数据、请求快照、内部步骤、业务幂等和结果事实。
- 通过主系统 Project Gateway 创建任务，**不直连 Agent**。
- 通过主系统统一业务队列接收运营按需请求，**不建立第二套运营排队入口**。
- 对回调、结果提交和事件使用**稳定幂等键**。
- 对未知副作用返回 `UNKNOWN`，**禁止自动重放完整业务过程**。

后端**不得**读取主系统数据库表或其他项目 Schema。跨项目数据通过数据拥有方 API 或冻结快照获得。

## 9. Windows 执行器

- 每个执行器目录**必须**包含符合 Agent Schema 的 `rpa-project.yml`。

执行器必须：

- 由实际中心 Task 驱动，**不注册 Windows 计划任务或常驻中心轮询**。
- 使用 `executorKey` 与根清单声明一致。
- 只处理当前 Task 的项目内部窗口、商品和批次，**不把它们重新建模为中心 Task**。
- 从受保护上下文引用获取任务输入，**不持有数据库账号**。
- 通过项目后端提交结果，由后端负责业务事务和幂等。
- 输出结构化事件、脱敏日志、最终报告和退出事实。
- 在取消、租约过期和 Claim 失效时**安全停止并保留证据**。

版本约束：

- **普通项目升级不得要求升级 Agent**。只有新增平台级运行时、制品协议或系统能力时才升级 Agent。

## 10. 数据库迁移

- 每个项目**默认**拥有独立 Schema；TEST 和 PRODUCTION 分离。
- **只允许**平台批准的 Flyway、Liquibase 等迁移适配器。
- **禁止**仓库提供任意 PowerShell、Shell 或宿主机可执行迁移命令。
- 每次迁移**必须**提供校验文件，并使用 Expand/Contract 等向后兼容方式。
- 数据库迁移成功不等于应用健康；发布**必须**继续通过 readiness 和黑盒测试。
- 代码回滚**不自动执行**数据库降级脚本。

### 10.1 后端镜像必须把应用根目录放在 `/opt/tyt-rpa/app`

- Controller 不从仓库取迁移脚本，而是从**已发布的后端镜像**里提取——迁移与镜像同属一个不可变制品，不会出现"镜像是 A 版、迁移是 B 版"。
- 提取路径是平台固定约定（逐字保留）：

```text
/opt/tyt-rpa/app/<database.migration.path>      迁移脚本目录
/opt/tyt-rpa/app/<database.migration.checksumFile>   校验文件
```

- 其中两个相对路径来自根清单 `database.migration` 的声明，**前缀 `/opt/tyt-rpa/app` 是写死的**。
- 后端 Dockerfile 必须（逐字保留）：

```dockerfile
WORKDIR /opt/tyt-rpa/app
COPY migrations ./migrations
COPY migrations.sha256 ./migrations.sha256
```

- 用 `WORKDIR /app` 之类的其他目录：镜像本身能正常跑，CI 与门禁也全绿（门禁在 conformance 模式下不做迁移），但**发布到 `MIGRATE_SCHEMA` 步骤才会失败**，报错（逐字保留）：

```text
Could not find the file /opt/tyt-rpa/app/migrations/. in container rpa-extract-<id>
```

  故障点离根因很远，且只在真正发布时才暴露。
- 多组件 monorepo 若习惯把工作目录设在子包（如 `WORKDIR /app/apps/backend`），**迁移必须仍然位于 `/opt/tyt-rpa/app` 下**，可在 `COPY` 之后再切换工作目录。

### 10.2 校验文件里的路径必须相对迁移目录，不是相对仓库根

- Controller 提取的是 `migrations/` 的**内容**，校验时用"相对迁移目录的路径"作为键。因此校验文件里**只能是裸文件名**（正误对照，逐字保留）：

```text
3ed82cbf...  V1__create_acceptance_tables.sql      正确
3ed82cbf...  migrations/V1__create_acceptance_tables.sql   错误
```

- 生成方式是**进入迁移目录再算**，而不是在仓库根算（逐字保留）：

```bash
cd migrations && sha256sum *.sql > ../migrations.sha256
```

- 在仓库根用 `sha256sum migrations/*.sql` 生成会带上 `migrations/` 前缀，键对不上，报错（逐字保留）：

```text
Migration checksum inventory does not declare <文件名>
```

- **注意此时文件哈希其实完全正确**，只是路径基准不同——不要照着哈希去排查。

## 11. 项目任务契约

- 按需任务**必须**提供三类契约文件（路径模板，逐字保留）：

```text
contracts/task-types/<taskType>.input.v<version>.schema.json
contracts/task-types/<taskType>.ui.v<version>.schema.json
contracts/reports/<reportType>.v<version>.schema.json
```

- 项目后端创建任务时**只提交稳定引用**（请求 JSON 示例，逐字保留）：

```json
{
  "taskType": "AUTO_PARTS.LISTING",
  "businessRequestId": "REQ-1001",
  "executorKey": "auto-parts-draft",
  "contextRef": "project://tasks/REQ-1001/context"
}
```

- 主系统保存 Task、Attempt、Claim 和引用；详细业务输入由项目后端冻结并通过 `contextRef` 提供。

### 11.1 项目后端调用主系统：签名约定

- 项目后端服务端到服务端调用主系统（创建任务、SSO 交换、读取导出数据等）时，**必须使用下面这一套签名，不得自创头名或字段顺序**。平台只认这一套；每接一个项目多一种签名方案，认证代码就会长出一条只服务于某个项目的分支。
- 请求头（逐字保留）：

| 头 | 内容 |
|---|---|
| `X-Project-Client-Id` | 平台下发的 `RPA_PROJECT_SERVICE_CLIENT_ID` |
| `X-Project-Secret-Version` | 平台下发的 `RPA_PROJECT_SERVICE_SECRET_VERSION` |
| `X-Project-Signature-Version` | 签名算法版本 |
| `X-Timestamp` | **毫秒**级 Unix 时间戳（JS 直接用 `Date.now()`，不要除以 1000） |
| `X-Nonce` | 单次随机串 |
| `Idempotency-Key` | 写操作必带；读操作留空 |
| `X-Signature` | 下面签名串的 HMAC-SHA256，十六进制小写 |

- 签名串按顺序换行拼接，**空值参与拼接为空串，不得省略该行**（逐字保留）：

```text
签名算法版本
clientId
大写 HTTP 方法
含 query 的完整路径          ← 例如 /api/rpa/exports/x?startDate=A&endDate=B
时间戳
nonce
幂等键
sha256(请求体)              ← 无体时是空串的 sha256
```

- 密钥为 `RPA_PROJECT_SERVICE_SECRET`。
- 三点易错（契约事实，必须遵守）：
  - **路径与 query 是同一行**，不是分开两行；query 要和实际发出的顺序一致。
  - **clientId 和签名算法版本在签名串里**，不只在请求头里。
  - **时间戳是毫秒**。平台按毫秒解析并做时钟偏移校验，秒级值会被读成 1970 年，在**比对签名之前**就判定超出偏移窗口。症状是 401，但签名本身可能完全正确——日志里看不出是哪一半错了（曾让一次联调白跑一轮）。
- 平台侧按 `X-Project-Client-Id` 查凭据、按 `X-Project-Secret-Version` 选当前或上一版密钥（**轮换期内旧版本仍可用**），校验通过后把租户和应用 ID 注入请求属性。
- **租户一律来自凭据，项目不得通过参数指定租户**。

### 11.2 平台开放给项目的读取接口

- 目前**只有**一个。新增接口一律走这一节登记，**不要口头约定**。

#### 采集日结数据导出

```
GET /api/rpa/exports/collection-daily-results?startDate=YYYY-MM-DD&endDate=YYYY-MM-DD
→ { "code": 200, "data": { "rows": [ ... ], "total": n } }
```

每行字段（camelCase）：

```
statisticDate, accountName, managerName, category, platform,
salesAmount, taxAmount, pageViews, visitors, orderCount
```

行为约定（三条都会影响项目侧取数逻辑）：

- **只返回 `SUCCEEDED` 的采集记录。** 失败记录在库里存的是 0，导出去会被读成"这家店当天没卖出去东西"，而不是"这天没采到"——那是错数，不是缺口。项目侧看到某天行数偏少，应当理解为部分店铺当天采集失败，而不是这些店铺没有营业。
- **窗口上限 400 天；命中行数上限（20000）时直接报错，不截断返回。** 截断的一页对只记录"最后看到的日期"的调用方来说像是完整答案，超出的日期再也不会被请求。错误码（逐字保留）：`RPA_COLLECTION_EXPORT_WINDOW_TOO_LARGE` / `RPA_COLLECTION_EXPORT_RANGE_INVALID`。
- **租户来自凭据**，不能通过参数指定。

## 12. 密钥和配置

- Git 只保存空值模板和键名说明。
- 密钥按 `项目 + 环境 + 组件` 隔离，由 Controller 或 Agent 临时注入。
- 项目**不得**把密钥写入清单、任务输入、命令行、日志、报告、截图名或构建制品。
- Windows 执行器临时密钥文件使用**最小 ACL**，任务结束**立即删除**。
- 生产配置**不得依赖**开发人员交互用户环境或开发机代理状态。

### 12.0 后端容器的运行期环境变量

- 密钥走 §12.1 的文件目录，**非密钥的运行期标识走环境变量**，由 Controller 注入（逐字保留）：

| 变量 | 取值 | 说明 |
|---|---|---|
| `RPA_APP_KEY` | 清单的 `appKey` | |
| `RPA_ENVIRONMENT` | `PRODUCTION` / `TEST` | **判断运行环境只能用它** |
| `RPA_RELEASE_VERSION` | 发布版本号 | 必须由 `/platform/version` 原样返回 |
| `RPA_SOURCE_COMMIT` | 源码 commit | |
| `RPA_CONFIG_VERSION` | 配置版本，可能为空串 | |
| `RPA_COMPONENT_KEY` | `frontend` / `backend` | |
| `PORT` | 清单声明的端口 | |

- **平台不注入 `NODE_ENV`**，也不注入任何项目自定义前缀的变量。
- 用 `NODE_ENV === 'production'` 之类判断环境，在生产里会恒为假——若项目据此在"生产走控制面、否则走本地 stub"之间切换，结果是**生产环境静默运行在 stub 模式**：SSO 兑换不发起任何请求就返回 401，且项目自己那句 `if (production && mode !== 'control-plane') throw` 的保护因为 `production` 恒假而永不触发。这个故障在 CI 与门禁里都发现不了。
- 更稳妥的写法：**不要引入"生产"这个开关**；参照实现只区分 `RPA_CONFORMANCE_MODE`，非一致性模式一律走控制面，没有第三种可能。

### 12.1 后端容器的运行期密钥目录

- Controller 把该组件的密钥物化到容器内 `/run/tyt-rpa/secrets/`，**一个文件一个密钥，只读挂载**。
- 后端**从该目录按文件名读取，不从环境变量读取密钥值**。
- 平台下发清单（除项目自己声明的密钥外，逐字保留）：

| 文件名 | 下发条件 | 用途 |
|---|---|---|
| `RPA_PROJECT_SERVICE_CLIENT_ID` / `_SECRET` / `_SECRET_VERSION` | 所有后端 | 调用主系统受控接口的 HMAC 身份 |
| `RPA_CONTROL_PLANE_BASE_URL` | 所有后端 | 主系统基址 |
| `CONTROL_PLANE_TLS_CA_CERTIFICATE` | 所有后端 | **验证主系统 TLS 证书的信任锚** |
| `DATABASE_HOST` / `DATABASE_PORT` / `DATABASE_SCHEMA` / `DATABASE_RUNTIME_USERNAME` / `DATABASE_RUNTIME_PASSWORD` | 清单声明 `database` | 运行期数据库连接 |
| `DATABASE_TLS_CA_CERTIFICATE` | 清单声明 `database` | 验证数据库 TLS 证书 |

注意：

- 主系统使用私有签发的证书，后端**必须**用 `CONTROL_PLANE_TLS_CA_CERTIFICATE` 建立信任，否则 SSO 授权码兑换会在 TLS 握手阶段失败。Node 项目在镜像中设（逐字保留）：
  `ENV NODE_EXTRA_CA_CERTS=/run/tyt-rpa/secrets/CONTROL_PLANE_TLS_CA_CERTIFICATE`
  （Node 只在进程启动时读取该变量）。
- **严禁**用 `NODE_TLS_REJECT_UNAUTHORIZED=0` 或等价的"跳过证书校验"手段绕过。
- `DATABASE_RUNTIME_HOST` 是 Controller 内部用于 `CREATE USER`/`GRANT` 的账号主机限定模式（如 `%`），**不是可连接的主机名**，**不会下发给应用**；连接地址用 `DATABASE_HOST`。
- 上表是**生产运行期**的下发清单。在中央黑盒门禁里，候选容器以 `RPA_CONFORMANCE_MODE=true` 启动，**整张表中的数据库相关项都不会下发**，后端**必须能无数据库启动并通过所有契约场景**。
- 读密钥时**不要为数据库参数写兜底默认值**（`?? '127.0.0.1'` 之类），否则"没下发"会退化成"连了个错地址"，最终表现为门禁就绪探测超时且根因难查。（交叉引用：规范 11 §15.14）

## 13. 开发完成定义

- 项目只有**同时**满足以下条件才算可直接接入：
  - 根清单及所有执行器清单通过平台 Schema。
  - 前端、后端、执行器和迁移均可由 CI 独立构建。
  - OpenAPI、任务输入、UI、事件和报告契约版本化并通过兼容测试。
  - TEST 环境可以由主系统一次发布完成，不需要服务器手工操作。
  - 项目入口自动登记，用户通过主系统通用容器完成登录和权限校验。
  - 项目后端可通过 Project Gateway 创建任务，Agent 可执行对应不可变制品。
  - 结果可回到项目后端并形成业务终态和主系统审计关联。
  - 发布、回滚、停用和卸载均通过主系统完成。
- 任何需要修改主系统固定菜单、复制用户权限、手工配置 Nginx、手工复制生产代码或直接修改主系统数据库才能上线的项目，**均不符合本规范**。

2. 平台能力未上线时可提前开发与契约门禁，但不得绕过主系统手工模拟为已接入生产（§1）。
3. 项目不得复制主系统用户表、角色表、部门表、全局业务队列、Task 状态机或节点调度器（§3）。
4. 一个业务项目必须只有一个生产源码仓库；组件用途只能由 `rpa-application.yaml` 声明，不能按目录名猜测；一个执行器只能属于一个 `appKey`（§4）。
5. 项目不得依赖仓库外相对路径、本机目录或未登记的其他仓库（§4）。
6. 仓库根必须提供 `rpa-application.yaml`，`apiVersion` 必须是平台已支持版本（示例为 `tyt-rpa/v1`）（§5、§6）。
7. `appKey` 发布后不可变，格式 `[a-z0-9][a-z0-9-]{1,62}[a-z0-9]`（3–64 字符），不能以连字符开头或结尾，不能占用平台保留命名空间（§6、§6.2）。
8. `components` 只允许 `frontend`、`backend`、`executors` 三个键，多余键即判非法；`WEB_FRONTEND`/`WEB_BACKEND` 必须声明 CPU、内存、PID、临时盘限制；服务端组件统一交付 Docker 镜像，执行器统一交付不可变制品（§6）。
9. 权限 code 必须以 `<appKey>:` 开头且必须包含 `<appKey>:project:view`；`permissions[].code`/`.name` 上限 160/200 字符（§6、§6.2）。
10. 执行器 `key` 不得重复；所有执行器 `taskTypes` 合并后不得重复；执行器清单 `projectKey` 必须等于根清单 `appKey`；执行器 `key` 格式 `[a-z0-9][a-z0-9._-]{1,99}` 小写（§6、§6.2）。
11. 根清单不得包含密码、Token、数据库连接串、生产域名或服务器地址；组件路径必须在仓库内，禁止绝对路径、目录穿越、符号链接和 Junction 逃逸；未被 Schema 声明的字段必须拒绝，不能静默忽略（§6）。
12. 资源边界：`resources.cpus` 0.1–8、`memoryMb` 64–8192、`pidsLimit` 32–2048、`tmpfsMb` 16–512、`backend.port` 1–65535、`image` 500 字符（§6.2）。
13. `taskTypes[]` 必须全大写 `[A-Z][A-Z0-9_.-]{1,127}`；`requiredCapabilities[]` 必须全大写且不含连字符和点 `[A-Z][A-Z0-9_]{1,63}`；`database.primarySchema` 小写下划线 `[a-z][a-z0-9_]{1,62}` 不能用连字符（§6.2）。
14. `navigation` 可选；目录与页面二选一（有 `children` 不能有 `route`，两者都没有即判非法）；深度最多 5 层，节点总数最多 200（整棵树）；`navigation[].key` 以 `[a-z0-9]` 开头结尾、最长 64、同级唯一（§6.1、§6.2）。
15. `route` 必须是同源相对路径：单个前导 `/`，禁止 `//host`、绝对 URL、`..` 穿越和反斜杠；后端用表单 `route` 拼重定向前必须自行再次校验（§6.1、§7）。
16. `status: PLANNED` 声明但不投影；实现后改成 `AVAILABLE` 并重新发布菜单才出现；`sys_menu` 无禁用态（§6.1）。
17. 前端必须支持 `embedded=true` 并隐藏自身全局导航与重复登录入口；声明 `navigation` 的项目嵌入时必须隐藏自身侧边栏、能按透传 `route` 直达页面（§7）。
18. 前端 `basePathMode` 固定 `RELATIVE`；调自己后端必须用相对路径且带 `credentials: 'same-origin'`，禁止 `fetch("/platform/session")` 式根路径写法（应用挂在 `/project-apps/<appKey>/` 前缀下）（§7）。
19. 前端不得写死主系统域名、生产域名或 API 主机；按钮权限必须后端同时校验；不保存主系统 JWT；处理会话过期回到主系统通用容器（§7）。
20. 后端必须提供健康、就绪、版本接口（示例路径 `/platform/health`、`/platform/readiness`、`/platform/version`），只用 Controller 注入的项目专属账号访问当前项目 Schema（§5、§8）。
21. 后端必须通过 Project Gateway 创建任务、不直连 Agent；必须走统一业务队列，不建第二套运营排队入口；回调/结果/事件用稳定幂等键；未知副作用返回 `UNKNOWN`，禁止自动重放（§8）。
22. 后端不得读取主系统数据库表或其他项目 Schema；跨项目数据走数据拥有方 API 或冻结快照（§8）。
23. 每个执行器目录必须含符合 Agent Schema 的 `rpa-project.yml`；由中心 Task 驱动，不注册 Windows 计划任务或常驻轮询；`executorKey` 与根清单一致；不持有数据库账号；通过项目后端提交结果（§9）。
24. 普通项目升级不得要求升级 Agent，只有新增平台级运行时、制品协议或系统能力才升级（§9）。
25. 数据库迁移只允许平台批准的 Flyway、Liquibase 等适配器；禁止仓库提供 PowerShell/Shell/宿主机可执行迁移命令；迁移成功不等于健康，发布必须通过 readiness 和黑盒测试；回滚不自动执行降级脚本（§10）。
26. 后端镜像应用根目录必须为 `/opt/tyt-rpa/app`（前缀写死），Dockerfile 必须 `WORKDIR /opt/tyt-rpa/app` 并 `COPY migrations ./migrations`、`COPY migrations.sha256 ./migrations.sha256`；放错目录只在 `MIGRATE_SCHEMA` 发布步骤报 `Could not find the file /opt/tyt-rpa/app/migrations/. in container rpa-extract-<id>`（§10.1）。
27. 迁移校验文件只能含裸文件名（相对迁移目录），禁止 `migrations/` 前缀；生成命令 `cd migrations && sha256sum *.sql > ../migrations.sha256`；路径基准错误报 `Migration checksum inventory does not declare <文件名>`，哈希本身正确（§10.2）。
28. 按需任务必须提供 `contracts/task-types/<taskType>.input.v<version>.schema.json`、`<taskType>.ui.v<version>.schema.json`、`contracts/reports/<reportType>.v<version>.schema.json`；创建任务只提交稳定引用（`taskType`、`businessRequestId`、`executorKey`、`contextRef` 如 `project://tasks/REQ-1001/context`）（§11）。
29. 项目调主系统必须用文档这套签名、不得自创头名或字段顺序；请求头 `X-Project-Client-Id`、`X-Project-Secret-Version`、`X-Project-Signature-Version`、`X-Timestamp`（毫秒）、`X-Nonce`、`Idempotency-Key`（写操作必带）、`X-Signature`（HMAC-SHA256 十六进制小写）（§11.1）。
30. 签名串顺序：签名算法版本 / clientId / 大写 HTTP 方法 / 含 query 的完整路径（同一行，query 顺序与发出一致）/ 时间戳 / nonce / 幂等键 / sha256(请求体)（无体为空串的 sha256）；空值拼为空串不得省略该行；clientId 和算法版本也在签名串内；密钥 `RPA_PROJECT_SERVICE_SECRET`（§11.1）。
31. 时间戳必须是毫秒（JS 用 `Date.now()` 不要除以 1000）；秒级值被读成 1970 年在比对签名前就超偏移窗口，症状是 401 但签名正确（§11.1）。
32. 租户一律来自凭据，不得通过参数指定；平台按 `X-Project-Secret-Version` 轮换期内新旧密钥都可用（§11.1、§11.2）。
33. 平台开放读取接口目前仅 `GET /api/rpa/exports/collection-daily-results?startDate=YYYY-MM-DD&endDate=YYYY-MM-DD`，返回 `{ "code": 200, "data": { "rows": [ ... ], "total": n } }`，行字段 camelCase：`statisticDate, accountName, managerName, category, platform, salesAmount, taxAmount, pageViews, visitors, orderCount`；只返回 `SUCCEEDED` 记录；窗口上限 400 天、命中行数上限 20000 直接报错不截断；错误码 `RPA_COLLECTION_EXPORT_WINDOW_TOO_LARGE` / `RPA_COLLECTION_EXPORT_RANGE_INVALID`；新增接口一律在 §11.2 登记（§11.2）。
34. Git 只保存空值模板和键名说明；密钥按 项目+环境+组件 隔离临时注入；密钥不得写入清单、任务输入、命令行、日志、报告、截图名或构建制品；执行器临时密钥文件最小 ACL 且任务结束立即删除（§12）。
35. 判断运行环境只能用 `RPA_ENVIRONMENT`（`PRODUCTION` / `TEST`）；平台不注入 `NODE_ENV`；`RPA_RELEASE_VERSION` 必须由 `/platform/version` 原样返回；参照实现只区分 `RPA_CONFORMANCE_MODE`，不引入"生产"开关（§12.0）。
36. 密钥物化在容器内 `/run/tyt-rpa/secrets/`，按文件名读取、不从环境变量读密钥值；后端必须用 `CONTROL_PLANE_TLS_CA_CERTIFICATE` 建立对主系统 TLS 的信任（Node 设 `ENV NODE_EXTRA_CA_CERTS=/run/tyt-rpa/secrets/CONTROL_PLANE_TLS_CA_CERTIFICATE`）；严禁 `NODE_TLS_REJECT_UNAUTHORIZED=0` 绕过（§12.1）。
37. `DATABASE_RUNTIME_HOST` 是 Controller 内部 `CREATE USER`/`GRANT` 主机限定模式（如 `%`），不下发给应用；连接地址用 `DATABASE_HOST`（§12.1）。
38. 门禁中 `RPA_CONFORMANCE_MODE=true` 启动时数据库相关密钥全部不下发，后端必须能无数据库启动通过所有契约场景；读密钥不得写数据库参数兜底默认值（如 `?? '127.0.0.1'`）（§12.1）。
39. 开发完成定义八项全满足才可直接接入：清单过 Schema、CI 独立构建、契约版本化过兼容测试、TEST 一次发布无需手工、入口自动登记、Gateway 建任务、结果形成业务终态与审计关联、发布/回滚/停用/卸载均走主系统（§13）。
40. 需修改主系统固定菜单、复制用户权限、手工配置 Nginx、手工复制生产代码或直接修改主系统数据库才能上线的项目均不符合本规范（§13）。
