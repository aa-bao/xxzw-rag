## 9. G5 Task 与 Windows 执行闭环（§8）

### 9.1 按需任务链路（原文逐字）

```text
项目运营页面或受控事件
  -> 主系统全局业务队列
  -> Task / Attempt / Claim
  -> 符合职责和能力的 Agent
  -> 不可变 Windows 执行器
  -> 项目后端结果接口
  -> Task 终态和项目业务终态关联
```

### 9.2 必须验证（R8-1 ~ R8-8）

| 编号 | 强制要求 |
|---|---|
| R8-1 | 项目后端 HMAC 服务身份、Nonce、时间偏差和签名版本。 |
| R8-2 | 相同 `businessRequestId + Idempotency-Key` **不重复创建**。 |
| R8-3 | Agent **只**领取匹配 `executorKey`、能力、职责和环境的 Task。 |
| R8-4 | Task JWT 绑定租户、应用、执行器、Task、Attempt、节点和 Claim。 |
| R8-5 | 旧 Claim、取消 Claim、过期 JWT 和错误 Audience **被拒绝**。 |
| R8-6 | 执行器**不持有数据库账号**，**不直连主系统数据库**。 |
| R8-7 | 结果重复提交幂等；结果提交失败**只重放提交，不重跑浏览器业务**。 |
| R8-8 | 项目进程退出码、信号、stderr、事件、报告和产物**完整可追踪**。 |
| R8-9 | 副作用未知时进入 **`UNKNOWN`**，**禁止自动整体重跑**。 |

```json

  },

```

### 13.2 字段与取值说明（逐字段）

| 字段路径 | 类型/取值 | 说明 |
|---|---|---|
| `appKey` | 字符串（示例值 `auto-parts-listing`） | 项目应用标识 |
| `commitSha` | 字符串（`<full-sha>` 占位） | **完整** Commit SHA |
| `manifestHash` | 字符串（`<sha256>` 占位） | 根清单 Hash |
| `contractHashes` | 对象（示例为空 `{}`） | 契约 Hash（OpenAPI、Schema 等）集合 |
| `components` | 数组（示例为空 `[]`） | 组件清单 |
| `tests.unit` | 枚举（示例 `"PASS"`） | 单元测试证明 |
| `tests.integration` | 枚举（示例 `"PASS"`） | 集成测试证明 |

## 16. 附录：已知 CI/CD 与部署实操坑（§15，15.1–15.14）

> 背景（原文逐字要点）：以下问题在 `tyt-independent-acceptance-app`（G2/G3 门禁的独立验收应用）第一次真正跑通
> `build -> gate -> register` 全链路、以及随后第一次真正执行生产部署时逐一发现；除特别注明外均已在平台仓库
> `xxzw-jokic/tyt-rpa` 修复。后续项目按本规范接入时会复用同一套 `project-contract-gate.yml` / `project-release-register.yml`
> 可复用工作流。**15.1–15.6 属于 CI/CD 链路，15.7 起属于部署与验收链路。**以下每条的"规避/修复"为原文给出的规定动作。

| # | 坑（现象/根因） | 规避/修复/规定动作（原文） |
|---|---|---|
| 15.1 | `git archive --format=zip` 每个条目 mtime 取归档时系统时间，同 commit 重打包两次字节完全不同，与不可变证据冲突 | `git archive` 加 **`--mtime="@$(git show -s --format=%ct <commit>)"`**，固定用 commit 自身时间戳，同 commit 永远产出字节一致归档 |
| 15.2 | Actions 密钥掩码会静默吞掉含密钥子串的 `$GITHUB_OUTPUT`（`Skip output 'xxx' since it may contain secret`）；门禁 Job 密钥近 20 个，短值（如数据库端口）易随机命中；可选密钥留空会被注册空字符串掩码吞掉**所有**输出 | 排查顺序：① 用非空哨兵值（如 `__unused__`）排除空可选密钥；② 输出 `probe=hello` 对照区分"命中子串"与"全局 bug"；③ Base64 编码**不能**保证绕过。**根治方案**：非密钥结构化数据（URI、摘要）不经过 `$GITHUB_OUTPUT`，写入 JSON 文件用 `actions/upload-artifact` 上传，下游 `actions/download-artifact` 下载读文件（掩码不扫描构件内容） |
| 15.3 | 自建 Runner 与主系统同宿主机，内部调用配局域网 IP（如 `http://192.168.1.67/...`）会被 `secureUrl()` SSRF 防护拒绝（只放行 `127.0.0.1`/`localhost` 明文 HTTP，局域网 IP 一律要求 HTTPS） | 同机内部调用应**显式使用 `127.0.0.1`**，不要用宿主机对外 IP |
| 15.4 | 可复用工作流 `project-contract-gate.yml` 新增 `actions/upload-artifact` 后，调用方 `release.yml` 顶层 `permissions:` 只给 `actions: read` → 启动前报 `Invalid workflow file`、`requesting 'actions: write', but is only allowed 'actions: read'` | 可复用工作流永远**不能申请比调用方更高的权限**；调用方顶层 `permissions:` 要**显式覆盖**到所有被调用工作流实际需要的权限（`write` 隐含 `read`，只需设最高需求档位） |
| 15.5 | 证据发布采用"同 commit + 同相对路径只能创建一次、内容不同即冲突"（`If-None-Match: *`）；同一 commit 重跑发布任何字节不同的证据（含逐次不同的 `ci-proof.json` 的 `workflowIdentity`）都触发 `Immutable evidence already exists with different content` | 排查非证据问题（凭据、权限）时先确认是否同 commit 重跑；若是，**推一个空改动产生新 commit 即可绕开**，问题自然消失 |
| 15.6 | **（未解决，仍在根因定位）** `project-publisher` 端点小 body 验签成功，真实 `publication.json`（约 8KB、含中文、多行 JSON、以 `\n` 结尾）稳定 401；服务端实际收到的字节数比发送少 1 字节（丢末尾换行）；与总字节数无关，`\n` 结尾必现；直连端口、换客户端均复现；两处防御性加固（`CachedProjectApplicationRequest` 显式循环读到 EOF、内部 HMAC 路径跳过 `RepeatedlyRequestWrapper` 重复包装）均未解决 | **临时规避**：确保签名请求体**不以 `\n` 结尾**（如序列化时不追加尾随换行）；根因修复前，走该内部 HMAC 通道、body 以换行符结尾的请求都可能被错误拒绝 |
| 15.7 | 用 `mv html html.old && mv html.new html` 原子切换目录，宿主机是新文件且 `nginx -s reload` 成功，但浏览器/curl 始终旧内容——Docker bind mount 绑定的是**目录 inode** 不是路径 | 修复两选一：**原地覆盖内容**（`rsync --delete` 或 `rm -rf <目录>/*` 后解包）；或 `mv` 切换后**重启容器**（`docker restart nginx-web`）。排查口诀：宿主机文件是新的但服务返回旧的，**先进容器看**（`docker exec <容器> cat ...`） |
| 15.8 | `http://<主机IP>` 访问主系统时项目入口容器报 `Cannot read properties of undefined (reading 'digest')`，iframe 不加载；`https://` 正常 | 根因：SSO 入口 PKCE 的 `code_challenge` 依赖 `crypto.subtle`，**只在安全上下文（HTTPS 或 localhost）**存在，HTTP 页面上为 `undefined`（`window.isSecureContext` 可判定）。**结论：不是缺陷，是浏览器平台约束；生产和验收一律用 HTTPS 访问主系统**；IP + 自签证书同样必须 HTTPS |
| 15.9 | 入口 iframe 显示 `{"code":500,"message":"INTERNAL_ERROR"}`，容器日志除 TLS 弃用警告外无任何信息——主系统私有签发证书，后端 `fetch` 兑换授权码时 TLS 校验失败（`UNABLE_TO_VERIFY_LEAF_SIGNATURE`），`fetch` 抛异常被顶层转成 500 | 修复：Controller 为每个 `WEB_BACKEND` 下发 **`/run/tyt-rpa/secrets/CONTROL_PLANE_TLS_CA_CERTIFICATE`**（与数据库 CA 完全对称）；项目按**规范 08 §12.1** 建立信任即可。排查提示：401/409 = 主系统拒绝（凭据、state、PKCE、重复消费）；500 = 请求根本没到主系统（TLS、DNS、网络）；`docker exec <后端容器> node -e "fetch('<控制面地址>')..."` 一步定位 |
| 15.10 | `SecretMaterializer` 每次发布 `rm -rf` 整个密钥目录再重建，换掉目录 inode；`DEPLOY_BACKEND` 在不可变标签一致时**复用**已有容器，复用容器 bind mount 仍指向旧 inode → 看到空目录，运行期重读密钥静默失败 | 修复：**原地清空目录内容**而非替换目录本身，保住 inode。**通用教训**：宿主机目录正被容器 bind mount 时，**不要用 `mv`/`rm -rf` 替换目录本身**，一律原地增删内容 |
| 15.11 | 页面在 iframe 渲染出结构和文案，但所有动态字段停在占位值（"检查中"、"--"），`catch` 都不触发，控制台无报错——CSP 设了 `default-src 'self'; ...` 但**没单独给 `script-src`**，回落到 `default-src 'self'` 而 `'self'` **不包含内联脚本**，`<script>...</script>` 被浏览器直接丢弃 | 修复：逻辑放**独立 `.js` 文件**并以 `<script src="./app.js">` 引用，服务端用 `text/javascript` 提供；**不要**通过加 **`'unsafe-inline'`** 解决（会废掉 CSP 对 XSS 的防护）。排查：curl 永远测不出来（不执行 CSP）；判据 = 页面结构/静态文案正常但动态字段停在初始值且无异常 → 优先怀疑 CSP 拦截，验收必须在浏览器里做并检查 CSP 违规告警 |
| 15.12 | 自托管 runner 与生产宿主机**同以 `tyt` 用户运行、共用同一 HOME**；工作流 `docker/login-action` 写 `~/.docker/config.json`，把 Controller 依赖的长期 PAT（`ghp_`）覆盖成 `GITHUB_TOKEN` 派生的安装令牌（`ghs_`，**1 小时即过期**），拉镜像能力一小时失效一次 | 修复：在 runner 的 `.env` 中设 **`DOCKER_CONFIG=/home/tyt/.docker-runner`**，登录写独立目录，互不干扰；改完需**重启 runner**。排查：令牌前缀 `ghp_`/`github_pat_` = 长期 PAT，`ghs_` = 短命安装令牌。通用教训：自托管 runner 与被部署服务同机同用户时检查是否共享 `~/.docker`、`~/.kube`、`~/.aws`，必要时环境变量隔离 |
| 15.13 | 新后端镜像**首次**发布必失败一次：`CHECK_BACKEND` 报 `curl: (7) Failed to connect ... after 1 ms`，人工重跑通过——`DEPLOY_BACKEND` 刚创建完容器立即探测，容器未绑定端口时连接**立即被拒**（毫秒级），`--max-time` 再大也没用 | 修复：readiness 探测加**有界启动宽限期（当前 90 秒、每 2 秒重试）**，且**只重试传输层失败**；响应体不匹配（版本不符）仍**立即失败**。通用教训：探测刚创建的进程必须区分"还没起来"（要等）与"起不来"（立刻报错） |
| 15.14 | 门禁候选运行时 `/platform/readiness` 连续 60 秒返回 503 到超时——后端在连 `127.0.0.1:3306` 而容器内没有该地址。门禁**刻意不注入任何 `DATABASE_*` 参数**、**刻意不把 fixture MySQL 接入候选容器 Docker network**；配置层兜底默认值（如 `?? '127.0.0.1'`）把"资源没下发"变成"连了个错地址"的模糊故障 | **正确做法**（参照实现 `tyt-independent-acceptance-app` 三层处理，照抄即可）：① 配置层 `database: conformance ? null : { ... }`，**不要写兜底默认值**；② 启动校验：conformance 下**跳过"必需密钥缺失"检查**；③ 数据访问层：无连接池时走**内存实现**——`health()` 直接返回健康；结果幂等用进程内 Map 按 Idempotency-Key 记住首次结果。**注意不能只改 readiness**：门禁会实际打一批 PROJECT 目标端点（清单见项目自己的 `contracts/platform-conformance-v1.json` 的 `scenarios`），都必须在无数据库前提下返回契约要求的状态码；"结果幂等"要求两次调用返回**相同的 id**（唯一真正需要状态）；fixture MySQL 是给门禁 runner 进程自己做跨 schema 隔离探测用的，通过 `PROJECT_CONTRACT_DB_*` 从宿主机直连（当前 `127.0.0.1:33316`），不经过候选容器，按 `databaseIsolation.projectSchema` 声明的 schema 名动态建库授权。**通用教训**：黑盒门禁运行环境是**受限的**，与生产不等价；生产由 Controller 下发、门禁不下发的资源（数据库最典型），应用必须有一条"没有它也能起来并满足契约"的路径 |

## 20. 本文件要点速览（30–50 条关键强制要求）

2. **任何门禁失败不得通过手工修改数据库状态绕过**（§2）。
3. 仓库必须在批准的 **`xxzw-jokic`** 组织；功能分支必须 **PR 合入受保护 `main`**；工作区干净 + **完整 Commit SHA** 已推送（§3）。
4. Git 跟踪文件、历史、测试夹具、构建制品**不得包含**密钥、Cookie、Token 或认证状态；依赖锁文件完整、依赖和许可证扫描通过（§3）。
5. 项目**不得**有任意下载执行、路径逃逸、未限制 Shell 或宿主机绝对路径；命中凭据扫描 → **`SECURITY_FROZEN`**，密钥轮换和历史清理前**禁止发布**（§3）。
6. `EMBEDDED_APPLICATION` 根清单 **`rpa-application.yaml`** 必须通过平台版本化 JSON Schema；`appKey`/组件 Key/执行器 Key/权限命名空间**唯一且稳定**（§4）。
